## 1. 目标与现状

升级应保留账号身份、当前有效凭据、项目、成员、历史事件、评估记录、证据及附件。用户不应因安装新版本而被导向一个空库，也不应在回滚时无提示地丢失升级后的新记录。

当前实现保留版本独立的数据库、私有配置和数据目录。7.1、7.6、7.7 分别使用 `jeauditflow_710`、`jeauditflow_760`、`jeauditflow_770`。这能隔离历史版本，但不等于已经实现多库自动合并或统一数据入口。

**7.7 目标库已有数据和后续写入时，必须保护目标库。不得把旧库整库覆盖到 7.7，也不得把旧密码哈希复制回来。** 旧库凭据与当前凭据不同，可能来自已完成的密码恢复；这属于需要说明的差异，不代表账号丢失。

本次新增的是只读盘点、主键差异比较、冲突预览、结构元数据指纹及过期计划检查。没有新增通用数据库迁移写入器，没有创建迁移版本台账，没有切换运行中数据源，也没有执行真实跨库迁移。下面的分阶段升级设计需要另行实现、演练和验收。

### 版本术语

| 名称 | 含义 | 不可混淆的内容 |
| --- | --- | --- |
| 应用版本 | 例如 `7.7.0` | 不等于数据库结构版本 |
| SQL 结构声明版本 | 当前数据库交付 manifest 的 `schemaVersion: 29` | 是交付声明，不能证明真实库曾完成全部结构迁移 |
| 工作区缓存结构版本 | Web 客户端 `DB_VERSION = 61` | 不等于 SQL 结构版本，也不是每个项目 JSON 都必有的字段 |
| 项目 revision | 项目协作修订号 | 同一项目的较大修订号不能被旧库较小修订号覆盖 |
| 迁移计划 | 本工具输出的脱敏 JSON | 不是数据库备份，也不是授权写入或迁移完成证明 |

## 2. 数据结构与保护边界

| 数据层 | 主要内容 | 迁移保护要求 |
| --- | --- | --- |
| 账号与用户资料 | `auditflow_accounts`、用户资料、角色与停用状态 | 保留稳定用户 ID；核对邮箱映射；当前目标库的凭据优先，禁止隐式重置 |
| 项目工作区 | `auditflow_projects.snapshot_json`、revision、owner | 保留完整 JSON、未知字段、正式范围、BP/GP、证据角色、评分和人工判断 |
| 项目关联 | 成员、评估记录、证据条目、事件 | 按真实主键比较；保留所有者、成员权限、原始 ID、来源与追溯关系 |
| 文件与附件 | 数据目录、FileAnalyst 附件二进制、定位和元数据 | 同时备份数据库与文件；校验大小、哈希及引用可解析性 |
| JiraFlow | 版本化状态与问题关联 | 保留原始关联；不在迁移过程中自动向外部 Jira 写入 |
| 临时状态 | sessions、项目锁、在线 presence | 不迁移为持久业务记录；切换后重新认证并重新获取锁 |
| 未识别扩展 | 未知表、未知 JSON 字段和额外列 | 原始保留并进入兼容审查，不静默删除或擅自解释 |

关系概览：账号通过稳定用户 ID 关联项目所有权和成员；项目通过项目 ID 关联事件、证据与评估记录；证据再关联原始文件和附件。正式评估结论仍由评估师确认。数据升级不能重算评分、把 Index-only 证据升级成直接证据、打开已关闭基线，或把 AI 建议转成正式结论。

表名与列布局以真实 SQL 元数据为准。只读工具会检查所有已发现的持久基础表，表格中的列举不是排除其他业务表的白名单。

## 3. 已实现：只读盘点和计划

### 3.1 安全行为

`local-deploy/scripts/data-upgrade-inventory.mjs` 直接使用已安装运行时中的 mysql2 驱动，不调用会自动建表、改表或更新会话的应用存储接口。

工具只连接本机回环地址，禁用多语句，使用 `REPEATABLE READ` 与 `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`。随后只执行元数据和行数据的 `SELECT`，最后 `ROLLBACK` 并关闭连接。非 InnoDB 基础表、连接失败、行数超限、缺少必要表、异常主键或未来版本都会阻止把计划视为可继续合并。

工具读取账号字段以比较身份与凭据，但不输出邮箱、姓名、真实用户/项目 ID、正文、密码哈希、盐或会话令牌。报告中的 `ref-...` 和 `hmac-sha256:...` 使用本机私钥生成，以避免低熵标识被普通无密钥哈希反查。

对 sessions、项目锁和在线 presence，工具只读取结构与数量，不读取会话令牌或其他行字段。

首次运行会创建本机私有文件 `local-deploy/runtime/data-upgrade/reference.key`，权限为 `0600`。这属于工具元数据写入，**不属于数据库写入**。报告文件也使用 `0600`，且拒绝覆盖已存在的路径。将私钥与公开发布包分开保管；不要上传私钥、配置文件、原始备份或客户数据。换钥后，不同批次的不透明引用和指纹不能直接比较。

### 3.2 可执行命令

在包含 `local-deploy` 的项目目录执行。下例显式检查当前关注的三个版本；不提供 `--versions` 时会按本机版本配置发现数据源，并始终包含目标版本。

```sh
node local-deploy/scripts/data-upgrade-inventory.mjs --help
node local-deploy/scripts/data-upgrade-inventory.mjs \
  --versions 7.1.0,7.6.0,7.7.0 \
  --target 7.7.0 \
  --output /tmp/jeauditflow-data-upgrade-plan-initial.json
```

`--output` 必须指向新文件。需要保留报告时，应使用受控的本机私有目录；`/tmp` 只用于上述演示，不是备份或长期审计存储。

确认前重新读取全部选定数据源，并验证旧计划是否仍适用：

```sh
node local-deploy/scripts/data-upgrade-inventory.mjs \
  --versions 7.1.0,7.6.0,7.7.0 \
  --target 7.7.0 \
  --verify-plan /tmp/jeauditflow-data-upgrade-plan-initial.json \
  --output /tmp/jeauditflow-data-upgrade-plan-rechecked.json
```

可用 `--project-root` 指定项目目录，`--key-file` 指定受保护的持久密钥，`--max-rows` 调整单表硬上限。默认上限为 100000 行，超过后整源标记为不可用，不会把截断结果当成完整数据。

退出码：

| 退出码 | 含义 | 后续动作 |
| --- | --- | --- |
| `0` | `no-change` 或 `review-required` | 查看计划；仍然没有写入器，也没有迁移授权 |
| `2` | `blocked` | 查看 `blockers` 和 `conflicts`；不能继续自动合并 |
| `1` | 参数、驱动、密钥、报告路径或过期计划等命令错误 | 修复错误后重新盘点 |

### 3.3 读懂差异

| 字段或分类 | 解释 |
| --- | --- |
| `missingFromTarget` | 源库某个真实主键在目标库中不存在；按键集合统计，不是按总行数猜测 |
| `targetOnly` | 目标库有而该源库没有的主键；通常包含升级后的新增记录，必须保留 |
| `divergent` | 主键存在，但完整规范化行不同；不算缺失 |
| `targetAhead` | 项目主键存在且目标 revision 更大；应保留较新的目标项目 |
| `schemaDiffersFromTarget` | 已读取的列结构元数据不同，进入显式结构兼容审查 |
| `credential-divergence` + `target-authoritative` | 同一身份的凭据不同；建议 `preserve-active-target-credentials`，不自动同步旧密码 |
| `preserve-active-target` | 涉及当前目标的差异保留目标现状；冲突仍需审查，不代表已自动解决 |
| `email-identity-collision` / `user-identity-collision` | 身份映射冲突；不能按相同邮箱直接串接到另一个用户 |
| `source-unavailable` | 源未读全；不能据此声称“旧数据全部已迁移” |

JSON 对象键顺序不同不会制造内容差异；数组顺序、未知字段和原始正文仍参与比较。比较覆盖事件、成员、评估记录及其他持久表，不仅检查账号与项目总数。

计划的 `checksum` 用于发现意外修改；它不是签名或写入权限。`--verify-plan` 重新盘点并比较带私钥的内容指纹。该检查不锁定后续业务写入，也不消除检查完成与未来写入之间的时间窗口；真正迁移时仍须冻结写入，并在同一受控阶段再次验证。

### 3.4 当前检查边界

盘点不是备份，不导出附件文件，不验证文件系统引用，不检查所有外键/索引/触发器，也不验证真实登录。每个数据库各自使用一致性快照，不存在跨多个独立数据库的全局同时快照。正式迁移前必须冻结全部选定源和目标，或建立经过验证的增量机制。

数据库交付 manifest 仅提供结构声明版本。工具读取真实基础表、列与主键元数据，并把元数据纳入指纹，但 `actualSchemaLedgerVerified` 仍为 `false`，不能把 manifest 数字当作真实结构迁移台账。项目格式只按专用 `workspaceFormatVersion`（当前上限 61）及已建立的 `snapshotPolicy: "metadata-only"` / `snapshotVersion` 信封（当前上限 2）判定；不把项目业务字段 `version`、`revision`、`schemaVersion`、`workspaceVersion` 等任意数值当作格式版本。对于没有现成版本标识的嵌入数据格式，未来版本识别仍需要专用适配器。

## 4. 待实现：统一数据入口和迁移流水线

建议将程序版本与业务数据生命周期分离。最新应用读取一个明确的“活动数据源”配置；安装新程序不能新建空业务库后直接切换。保留历史库作为受控只读恢复源，正常业务只向一个经验证的目标写入，避免多版本并行修改后再猜测哪个数据是最新的。

建议状态流程：

1. `DISCOVER`：盘点所有选定旧库和当前目标，记录版本、技术身份、结构及业务指纹。
2. `PLAN`：明确保留项、新增项、冲突处理和目标数据源；产生供审核的脱敏计划。
3. `BACKUP`：冻结写入后备份全部源库、当前目标、附件、配置映射和相关文件；在独立实例恢复演练。
4. `STAGE`：在新的隔离数据库应用有序结构迁移，再加载当前目标的完整基线，只补入经过审核的旧库缺失项。
5. `VERIFY`：核对主键、规范化内容、关系、附件、revision、人工判断、正式基线、登录和权限；保留验证回执。
6. `SWITCH`：再次核对冻结期指纹，原子切换活动数据源，记录前后映射和操作者。
7. `OBSERVE`：完成真实页面和业务验收，确认新写入持久化；原数据库和备份继续保留。
8. `COMPLETE` 或 `ROLLBACK`：完成验收后解冻；异常时按新写入边界执行恢复，不静默丢弃差异。

这些状态是后续设计。当前只实现第 1、2 步及第 5 步的一部分数据比较，尚没有事务化统一迁移引擎或活动数据源切换功能。

### 结构升级台账设计

新增独立 `schema_migrations` 台账，保存迁移 ID、前后结构版本、脚本校验值、应用版本、执行时间、状态和恢复引用。迁移脚本必须明确前置条件、幂等规则和预期结构，拒绝乱序、同 ID 不同脚本及不支持的未来版本。

MySQL 的 DDL 并不与所有 DML 组成一个可整体回滚的事务，不能仅凭 `ROLLBACK` 声称能够撤销建表或改表。应优先在隔离库完成结构升级与数据验证，再切换活动连接。失败的隔离库不能被标记为生产数据源。

### 冲突策略

| 场景 | 处理建议 |
| --- | --- |
| 旧库独有账号，且身份、邮箱均不冲突 | 在隔离目标保留原 ID、角色和凭据格式；按支持的算法验证，不能替换成公共默认密码 |
| 当前目标已有相同身份 | 当前凭据保持有效；元数据差异独立审核，不自动撤销刚完成的密码恢复 |
| 相同邮箱、不同用户 ID | 由管理员选择明确映射并保留映射记录；未经确认不合并所有权 |
| 旧库独有项目或关联记录 | 全量保留来源和原始 ID，核对所有者、成员与附件后再补入 |
| 相同项目 ID，目标 revision 更大 | 保留目标；旧快照归档，不回退项目修订 |
| 相同项目 ID、相同 revision、内容不同 | 视为分叉；人工决定保留、重命名恢复副本或逐项合并 |
| 事件/记录数相同但主键不同 | 识别为不同数据，不能凭行数宣告一致 |
| 无主键表、未知结构或未来版本 | 阻止自动合并，先实现适配和可验证的标识策略 |

禁止用一个全局“覆盖旧数据/覆盖新数据”复选框处理所有冲突。正式范围、人工评分、证据角色、评估师确认和关闭基线必须逐类保留其权限和审计来源。

## 5. 兼容与回滚策略

兼容不代表让旧应用任意写新结构。建议采用“旧数据只读适配 + 最新结构单一写入”的策略：读取时转换到内存中的标准模型，保留原始快照及未知字段；保存时由最新服务校验并按 revision 乐观锁写入。需要旧版运行时，连接其冻结前的配套数据库。

历史 JSON 不应只把 `version` 改成当前值就算迁移。每次转换应有明确输入/输出版本、字段映射和保真测试。碰到比当前软件新的数据，应只读显示解释或拒绝导入，不应降级覆盖。

| 回滚时点 | 可执行的恢复边界 |
| --- | --- |
| 切换前 | 继续使用原活动数据源；保留失败的 staging 诊断，禁止启动指向半迁移库的服务 |
| 切换后但尚无新写入 | 停止新服务，恢复已验证的原库与配套文件映射，再启动旧版；验证账号、项目与附件 |
| 切换后已有新写入 | 冻结目标并先备份新库、文件及新增变更；选择前向修复，或审查增量后恢复；不能只切回旧库后称“无损回滚” |

当前没有经过验证的自动反向迁移。回滚不能自动把 7.7 新增的事件、评估记录和附件写回 7.1/7.6。旧版本重新上线前，要明确告诉用户可见数据截止点及尚待恢复的新数据范围。

现有 `migrate-7.6-to-native-7.7.mjs` 是特定的 7.6 到空 7.7 目标复制工具，会拒绝非空目标或已有目标数据目录；它不是当前已使用 7.7 的多库合并工具。不要绕过其保护，也不要清空当前目标后强行重跑。

node --test local-deploy/scripts/data-upgrade-plan.test.mjs \
